**Date:** 2026-09-01
**Status:** In progress
**Reviewed commit:** `4dc4c62c7d080c5d29b8bf0d140b89a43533832c`, plus the uncommitted fixes described below

This review covers the hosted prover, operation recovery, and secret-bearing error paths.
It does not approve the release. The release still requires the remaining review sections,
the external install canary, and explicit owner approval.

## Verified mechanisms

- The operation journal binds the operation ID to the canonical request before proving.
- A conflicting request fails before the prover or submission RPC receives it.
- Erebus stores the signed transaction and its hash before submission.
- Startup reconciliation is read-only and never submits a transaction.
- Recovery resubmits the stored transaction without changing its hash.
- Erebus rebuilds a proof only when the recorded transaction cannot produce an effect.
- The hosted prover stores a completed one-time result before it returns that result.
- Prover-job files use mode `0600`. The prover-job directory uses mode `0700`.

These statements are source and test conclusions. They are not results from a new funded
mainnet run.

## Finding R1: A lost hosted-prover response could consume another proof job

**Severity:** Medium
**Status:** Fixed for transient failures and process restart before job-ID persistence

Failure sequence before the fix:

1. Erebus submitted a proof job with an idempotency key.
2. Starkscan accepted the job, but the HTTP response did not reach Erebus.
3. Erebus returned a transport error without repeating the exact request.
4. A later operation rebuild could submit a different proof request and consume more budget.

This failure did not create a duplicate chain payment. No Starknet transaction was signed at
this stage. The failure could waste prover budget and delay recovery.

Erebus now retries transient submit and poll failures with the same request. Before the first
submit, it also writes an operation-to-job index and the exact request to a mode-`0600` file.
After restart, `resume_operation` resubmits that same request with the same relay key, recovers
the original job, compares the proof against the preflight commitment, and continues the
original `Prepared` or `Proven` attempt. An expired proof follows the existing safe rebuild
path. Erebus removes the private request body as soon as the job ID is durable.

Two fault tests cover the lost-response boundary: one recovers in the running process and one
constructs a new `ProvingService` over the durable state. Both confirm exact body and
idempotency-key reuse. The restart test also confirms that neither the request body nor API
key remains in the completed cache.

Residual upstream limitation: Starkscan documents successful proof results as delivered once.
A process that stops after receiving that terminal HTTP response but before its atomic cache
write can still lose access to the result. Erebus cannot acknowledge delivery through the
current API. This can waste prover budget, but it cannot duplicate a chain payment because no
transaction has been signed at this boundary.

Reference: https://starkscan.co/docs/api/strk20-prover

## Finding R2: RPC error data could expose the pool private key

**Severity:** High
**Status:** Fixed

Failure sequence before the fix:

1. `compile_actions` sent the pool private key to the configured RPC in calldata.
2. The RPC returned a JSON-RPC error and included request data in `error.data`.
3. `RpcError` appended the complete data object to its public error text.
4. The CLI, Python SDK, and MCP server passed that text to the caller.

The source contained this path. The review did not find evidence that a production secret
entered the repository or a public log.

`RpcError` now emits only reviewed contract labels, such as `NON_ZERO_VALUE`. It never emits
the surrounding data object. Regression tests put a marker secret beside a valid label and
confirm that only the label remains.

## Finding R3: Transport and debug output could expose credentials in URLs

**Severity:** High
**Status:** Fixed

Alchemy credentials can appear in the RPC URL path. The default `reqwest` transport error
includes its request URL. Rust and Python configuration debug output also included complete
RPC and prover URLs.

Transport errors now omit endpoint details. Rust debug output keeps only the URL origin.
Configuration debug output redacts the complete RPC and prover URLs. Tests cover Rust, the
Python SDK, and MCP configuration objects.

## Finding R4: Malformed endpoint responses could enter public errors

**Severity:** High
**Status:** Fixed

Several malformed-response errors included the complete RPC or prover response. An endpoint
could place calldata or another secret marker in the response. The CLI and MCP server could
then return that marker to the caller.

Malformed-response errors now keep the field name and failure category. They do not include
the received value or response body. A regression test confirms that an invalid felt and an
invalid call result do not echo their values.

## Finding R5: Python grant debug output included the encrypted capsule

**Severity:** Medium
**Status:** Fixed

The Python `ViewingKeyGrant` dataclass used its default representation. Debug output therefore
included the complete encrypted capsule. The MCP result already omitted the capsule and wrote
it to a mode-`0600` file, but an application log could still expose it.

The dataclass representation now omits `viewing_key`. The existing file and MCP-result tests
still pass, and a new assertion covers the debug representation.

## Finding R6: Release publication happened before the artifact canary

**Severity:** High
**Status:** Fixed in the workflow, not yet run for v0.2.0

The tag workflow created a draft release and then published it immediately. The clean-install
canary started only after the complete wheel workflow ended. A broken package could therefore
become public before the canary found it.

The tag workflow now creates a draft release and stops. The owner must keep the draft private
until the artifact canary passes. Publishing the reviewed draft triggers the public-package
workflow. That workflow deploys the package index before it tests installation from the public
index on Linux and macOS.

The workflow files pass YAML parsing and the local release-readiness gate. The last successful
wheel and clean-install canaries were for v0.1.0 on 2026-08-19. They do not prove the v0.2.0
artifacts.
