# `v0.2.0` release plan

**Status: unpublished. Do not create or push the tag without explicit owner approval.**

Completed implementation and mainnet evidence are not repeated here. See
[`status.md`](./status.md), the
[`mainnet run record`](./runs/2026-08-31-mainnet-starkscan-workflow.md), and the
[`machine-readable gate`](./runs/v0.2-mainnet-canary.json).

## Release claim

`v0.2.0` is a **mainnet-verified, experimental, unaudited technical preview** of Protocol 4.
It is not production-ready. Erebus hides negotiation and settlement terms, not the public
channel relationship or transaction metadata.

## Remaining release gates

### 1. Reconcile final mainnet evidence

- Independently verify the committed second-canary record before adding it to the manifest
  or release claim.
- Verify every `strk20.json` transaction against the canonical mainnet pool.
- Ensure every public record omits secrets, grants, protected paths, proof blobs, and
  credential-bearing URLs.
- Keep the machine-readable release gate aligned with the evidence selected for release.

### 2. Finish end-to-end documentation

- Make `docs/runbook.md` the single clean-machine path from installation through two-agent
  mainnet settlement, recovery, observer inspection, and scoped disclosure.
- Document Starkscan hosted proving as the primary demonstrated path.
- Retain the local-prover path as an operator-controlled fallback, with its screening and
  RPC requirements stated explicitly.
- Test every command from a clean shell with placeholder-only configuration.
- Link the privacy model at each point where the operator might infer a stronger claim.

### 3. External clean-install canary

- Provide release-candidate artifacts to an operator outside the implementation path.
- Install without this checkout or a Rust toolchain.
- Confirm version `0.2.0`, Protocol 4, and thirteen MCP tools.
- Run mock and read-only operational checks.
- Record hidden prerequisites and repair the documentation.

A funded mainnet write is optional and requires a separate explicit authorization and fee
plan.

### 4. Targeted security and recovery review

- Review hosted-prover job persistence, idempotency, proof expiry, and exact-request reuse.
- Review the transaction journal, reconciliation, reservations, and restart behavior.
- Review key and grant redaction across Rust, CLI JSON, Python, MCP, logs, and errors.
- Resolve or explicitly block the release on every critical or high finding.

### 5. Final release-candidate gates

- Rust format, clippy, tests, and docs pass with warnings denied.
- Python tests and dependency hashes pass.
- TypeScript typecheck, build, and tests pass against the pinned oracle.
- Linux x86-64 and macOS arm64 wheels install and execute.
- Version parity, checksums, SBOM, skill contract, demo contract, and full-history secret scan
  pass.
- The replacement video and public demo work without authentication.

### 6. Owner release decision

Stop here and request explicit approval. Do not infer approval from a green canary, a sprint
deadline, or the presence of version `0.2.0` in source manifests.

## Publish sequence after approval

1. Freeze the reviewed commit and record its full hash.
2. Create the verified `v0.2.0` tag.
3. Let release automation build wheels, raw binaries, checksums, and the SBOM.
4. Create the GitHub release as a draft.
5. Publish and verify the static package index.
6. Install `erebus-mcp-server==0.2.0` from the public index on fresh Linux and macOS
   environments.
7. Confirm the installed CLI version, Protocol 4, thirteen-tool surface, and artifact canary.
8. Publish the GitHub release only after those checks pass.
9. Recheck all links and the sprint hub.

## Not required for `v0.2.0`

- OpenAI or another model-provider credit balance.
- A funded run through one specific agent framework.
- Deal Room, swaps, bridges, escrow, or new protocol features.
- Complete relationship privacy.
- A claim of production readiness.

Independent audit, encrypted backup/restore tooling, production monitoring, incident
response, spending controls, and a named long-term security maintainer remain post-preview
gates.
