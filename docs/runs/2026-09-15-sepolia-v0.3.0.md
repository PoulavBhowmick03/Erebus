# Sepolia run — 2026-09-15 (Protocol 5 / 0.3.0 onboarding)

> **Uncommitted canary.** This ran from the `metropolis` working tree with the 0.3.0 changes
> uncommitted, not from `main` or a release commit. It is supporting evidence for the onboarding
> change and the Protocol 5 client. It is **not** a clean release-from-main canary, and it does
> not establish that the released commit passed Sepolia.

This run exercises the two things the unreleased **0.3.0 / Protocol 5** change set adds: the
installed `erebus-init` onboarding, and a full
negotiate → settle → disclose loop on the Protocol 5 client. Everything was driven by the
source-tree `erebus-cli` built from that working tree; the packaged install path was exercised
separately by `scripts/check-onboarding-install.py`.

The payer is a wallet that already existed on this machine. The payee is a fresh identity this
run's `erebus-init` created, funded, and registered — that is the point of the run.

## Checks

- **Payment conserved.** Payer notes went `[1.0, 1.0] → [1.0]`; payee went `[0.1] → [0.1, 1.0]`.
  The settlement record carried `agreed_amount == paid_amount == 1000000000000000000` and
  `consistency: true`.
- **Scoped disclosure.** The payer granted a wire-v3 viewing key for deal
  `15006615881289598903` to a third identity (`0x73dde958…45b8b`, not a party) with a one-hour
  expiry. That identity's `reveal` returned exactly three offers — proposal, counter,
  acceptance — and the settlement. The grant carries no spending authority.
- **Recovery is clean.** `reconcile` classified every journal entry. The two deliberately
  failed attempts (below) both read back `no_effect`: no transaction was signed, so nothing
  reached the chain and nothing is left pending.
- **Fee is charged in public STRK, not from notes.** See the balance failure under "what
  fought us"; this is F36 again.

## What fought us

**1. Onboarding 403s against the endpoint the repo documents.** `erebus-init` failed twice with
an opaque `RPC request failed` against `publicnode`, which rejects the default
`Python-urllib` User-Agent. Logged and fixed as F43; a one-line header. This is the reason the
run could not simply be re-run to confirm the preceding note.

**2. Both directions must be opened, and the payee must be funded to do it.** A one-sided
channel open left the payee with `unknown channel handle`; a `rebuild_state` derived only the
payee's own (empty) record. The reference flow in `scripts/demo.sh` opens both directions, and
each side then reads the other's offers. That is one extra `apply_actions` on the payee side
(2 STRK) that a fresh identity does not budget for. Onboarding's default plan funds three
writes for the *creator*; it does not know the counterparty will need two (open + counter).

**3. The settlement failed on the public balance, not on notes or allowance.** With the price
agreed and a 1 STRK note in hand, `accept_and_settle` returned `INSUFFICIENT_BALANCE: public
balance … does not cover 5000000000000000000 (fee, deposit, and 3000000000000000000 reserved
for gas)`. The payer had spent its public STRK on the two earlier proofs and held only 4.01
STRK. Allowance was 96 STRK; the shielded balance was fine. F36 says this already; this run is
a second independent sighting, and it is worth restating for anyone budgeting a session: the
pool fee is pulled from public STRK through `transfer_from`, so neither a healthy shielded
balance nor a healthy allowance is sufficient on its own.

## What this run does not establish

It is one bounded workflow on a testnet. It is not evidence of capacity, uptime, independent
security review, or safe use with real value. The relationship, timing, action shape, and note
count remain public exactly as [privacy-model.md](../privacy-model.md) describes. The
settlement was driven through the CLI seam, not through an external agent framework over MCP;
the MCP transport was covered only by the packaged install check (thirteen tools served), not
by a live negotiation. The deal was 1 STRK, far below the ~18.4 STRK `reveal` boundary F40
recorded. Two failed writes were attempted and one extra top-up transaction was needed; the
transaction table lists them because they happened, not because a clean run would contain them.
And it ran from an uncommitted working tree: it says nothing about whether the release commit
itself passes Sepolia. Confirm on a clean checkout of the release commit before shipping.
